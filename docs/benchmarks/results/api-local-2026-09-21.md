# Local API read-path benchmark — 2026-09-21

This is a **loopback API-handler measurement only**. The target used the real
StreamForge HTTP handler with an in-memory reader. It excludes PostgreSQL,
Kafka, TLS, and network latency, and therefore is **not a full-system capacity
claim**.

## Workload and environment

- Endpoint: `GET http://127.0.0.1:18080/v1/games?limit=100`
- Fixture: 100 game records per response; response body size: 12,814 bytes
- Three measured 30-second runs, 16 concurrent load-generator workers, 2-second
  request timeout
- Host: Windows/amd64, AMD Ryzen 7 7700X, 16 logical CPUs
- Runtime: Go 1.26.5; StreamForge commit `9d5930f0c7737ab50aa47687e053fcd6bff77fec`

The benchmark fixture was started in one PowerShell terminal:

```powershell
$env:STREAMFORGE_BENCH_SERVER = "1"
go test ./internal/api -run TestBenchmarkServer -count=1
```

The following exact load-generator command was run once for each output path
(`run-1.json`, `run-2.json`, and `run-3.json`):

```powershell
go run ./cmd/loadgen -url "http://127.0.0.1:18080/v1/games?limit=100" -duration 30s -concurrency 16 -request-timeout 2s -metadata profile=api-local-c16 -metadata host=local-windows -metadata dataset=games -output ".\evidence\api-local-2026-09-21\run-N.json"
```

The first run that exhausted host threads while connection churn was present is
not retained as benchmark evidence. The three raw reports below were collected
after the load generator's per-host connection-pool bounds were added.
